# Агент поддержки и продаж магазина ПО

Хакатон «ИИ-Кузница», задача Softline. Агент отвечает клиентам магазина лицензий в чате на сайте:
- подбирает продукт и в случае, когда клиент знает, что ему нужно, и когда не знает;
- предлагает российские аналоги из реестра отечественного ПО;
- называет цену и наличие по каталогу;
- готовит черновики КП и счёта менеджеру;
- учится на ответах менеджера: ответ, отмеченный «Запомнить», агент использует для следующих клиентов.

Сложное и нестандартное агент передаёт человеку. Ориентир заказчика по нагрузке — около 500 обращений за полгода.

**Стенд:** https://kuznica-demo.codeboom.pro — чат клиента. Панель менеджера `/manager` открывается по токену. Логин для жюри — в описании сдачи.

## Модель и стоимость

Агент работает на **qwen3.5:9b** — модели с открытыми весами под лицензией Apache 2.0. Так требует заказчик: только открытые веса, не больше 128 ГБ видеопамяти при квантовании от Q4. В квантовании Q4_K_M файл модели весит 6,6 ГБ, а вместе с эмбеддингами bge-m3 (1,2 ГБ) всё помещается на одну видеокарту.

| Где работает модель | ₽ за запрос |
|---|---|
| Ollama на своём сервере с видеокартой (так работает стенд) | 0 ₽: токены не оплачиваются, данные клиентов не уходят наружу |

Расход каждого запуска в токенах и рублях пишется в `agent_runs` и выводится в `GET /api/manager/stats`. Средний запрос на стенде — около 14 тыс. входных и 600 выходных токенов за 2–3 шага агента.

## Как устроено

```
клиент ─► /api/chat ─► маскировка ПДн ─► агентный цикл (модель ⇄ инструменты, ≤ 8 шагов)
                                              │
              search_kb ── база знаний (pgvector + полнотекст)
              check_stock ── каталог из фида магазина (Postgres, полнотекст)
              get_price ── цену и скидки считает код, а не модель
              draft_proposal / draft_invoice ── черновики КП и счёта в базе
              handoff_to_manager ── эскалация
                                              │
                         сверка ответа ◄──────┘  каждое число в ответе должно быть в данных инструментов
                                              │
менеджер ◄─ /api/manager/* ◄─ очередь, КП в PDF «Черновик — на проверку менеджеру», «Подтвердить» / «Отклонить»
```

- **Цифры не выдумываются.** Цены, суммы, остатки и сроки модель берёт только из ответов инструментов. Перед отправкой ответ сверяется: каждое число должно найтись в данных. Не сошлось — модель исправляет ответ один раз, не сошлось снова — обращение уходит менеджеру.
- **Действия не выдумываются.** Если в ответе написано «подготовил КП», а инструмент не вызывался, сверка это ловит.
- **Персональные данные до модели не доходят.** Почта, телефоны, ИНН и имена заменяются метками (`Почта_1`). В черновик КП настоящие значения подставляются обратно уже на сервере.
- **КП уходит клиенту только после менеджера.** Агент делает черновик без подписи и печати. Менеджер смотрит PDF и нажимает «Подтвердить»: письмо уходит клиенту, и это записывается в журнал.
- **Устаревшие условия.** Куски базы знаний с истёкшим сроком помечаются, и агент не отвечает по ним, если есть действующие.
- **Учится на ответах менеджера.** Под ответом клиенту у менеджера есть флажок «Запомнить ответ». Отмеченная пара «вопрос — ответ» попадает в базу знаний: почта, телефоны и ключи лицензий из неё вырезаются. Следующий клиент с похожим вопросом получает ответ сразу, без менеджера. Без отметки ничего не запоминается. Список выученного виден в панели, у каждой записи есть кнопка «Забыть».
- **База знаний правится в панели.** Во вкладке «Сводка и БЗ» менеджер видит все статьи, может исправить текст, написать новую статью или удалить старую. При сохранении статья заново режется на фрагменты, и для них пересчитывается поиск. Агент видит правку со следующего вопроса. Исправленные в панели статьи не затираются, когда база магазина загружается заново.
- **Каталог обновляется сам.** Раз в сутки, в 04:00 МСК, приложение скачивает товарный фид магазина и заменяет каталог одной транзакцией, позиции пишутся в базу пачками прямо из потока. Если в фиде вдвое меньше позиций с ценой, чем было, каталог остаётся вчерашним. Цены в фиде с НДС.
- **Нет в наличии — не повод отказать.** Агент называет цену, делает КП и счёт, а поставку подтверждает менеджер.
- **Скидка до 5%.** Если клиент просит скидку, агент сам даёт 5%; сумму считает код. Больше 5% и отсрочка платежа — только менеджер.
- **Реквизиты в КП.** Агент просит название компании, ИНН и КПП. Черновик делает сразу, а недостающее менеджер дописывает сам.
- **Открытая модель.** По умолчанию Ollama с qwen3.5:9b. Ту же открытую модель можно взять у провайдера через любой OpenAI-совместимый шлюз.

Стек: Nuxt 4 / Nitro, Postgres 17 + pgvector + pg_trgm, эмбеддинги bge-m3, PDF на pdf-lib.

## Запуск

```
cp config.example.env .env        # заполнить: модель, пароль базы, токен менеджера
docker compose up -d              # Postgres с pgvector
npm i
python3 -I scripts/fetch_kb.py    # база знаний: публичные справочные страницы магазина → data/kb-softline/
npm run ingest -- --kb data/kb-softline
npm run ingest:feed -- <фид.xml>  # каталог из публичного YML-фида магазина
npm run dev
```

Без фида и страниц магазина можно запустить на синтетике: `npm run ingest` загрузит `data/` (описание в `data/README.md`).

### Модель и запасной путь

Модель выбирается переменной `NUXT_LLM_PROVIDER`. По умолчанию это `ollama`: своя модель на своём сервере (`NUXT_OLLAMA_BASE_URL`, `NUXT_OLLAMA_MODEL`, по умолчанию `qwen3.5:9b`, 0 ₽). Второй вариант — `gateway`: та же открытая модель у провайдера (`NUXT_LLM_BASE_URL`, `NUXT_LLM_API_KEY`, `NUXT_LLM_MODEL`). Модель шлюза задаётся явно, закрытой по умолчанию нет. Если ключ провайдера вписать в `.env` заранее, при падении GPU-узла достаточно сменить `ollama` на `gateway` и перезапустить сервер. Фид для ежедневного обновления — `NUXT_FEED_URL`; если он пустой, каталог не обновляется. Эмбеддинги (`NUXT_EMBED_BASE_URL`, bge-m3) живут на том же узле. Если они не отвечают, поиск по базе знаний сам переходит на полнотекст и триграммы, а к эндпоинту не обращается 5 минут, чтобы каждый ответ не ждал таймаут. Каталог от эмбеддингов не зависит.

Данные магазина (фид, страницы, переписка) принадлежат заказчику, поэтому в репозитории их нет. Здесь лежат только загрузчики. `fetch_kb.py` соблюдает robots.txt, делает один запрос в 4 секунды и не берёт личные контакты сотрудников.

## Telegram

Тот же агент отвечает в личных сообщениях бота. Группы бот не слушает.

**Что умеет**
- Отвечает на вопросы текстом. Ответ приходит с той же разметкой, что в веб-чате: жирный, списки, ссылки. Таблица приходит моноширинным блоком или списком. Длинный ответ режется на несколько сообщений по абзацам. Под ответом одной строкой указаны источники из базы знаний.
- Понимает голосовые сообщения, если включено распознавание речи (`NUXT_ASR_URL`, та же своя модель, что у диктовки в чате). Клиенту показывается, что распознано. Без распознавания бот просит написать текстом.
- Черновик КП клиенту не уходит. Клиент видит сообщение, что КП подготовлено и придёт после проверки. Когда менеджер нажимает «Подтвердить», PDF приходит в этот же чат.
- Ответ менеджера из панели приходит клиенту в Telegram. Если Telegram недоступен, ответ всё равно сохраняется в панели, а ошибка пишется в журнал.
- `/start` рассказывает, что умеет консультант, `/new` начинает новое обращение. Пока агент думает, над чатом горит «печатает…».
- Ограничения те же, что у чата на сайте: 10 сообщений в минуту на чат, общий потолок процесса, вопрос до 4000 символов.

**Как включить**
1. Создать бота у [@BotFather](https://t.me/BotFather) командой `/newbot` и скопировать токен.
2. В `.env` заполнить:
   - `NUXT_TELEGRAM_BOT_TOKEN` — токен бота;
   - `NUXT_TELEGRAM_WEBHOOK_SECRET` — длинная случайная строка из латиницы, цифр, `_` и `-`, например `openssl rand -hex 32`;
   - `NUXT_TELEGRAM_PUBLIC_URL` — публичный адрес стенда с https;
   - `NUXT_TELEGRAM_API_URL` — только если стенд ходит в Telegram через прокси. По умолчанию это `https://api.telegram.org`.
3. Перезапустить приложение и поставить вебхук:
   ```
   npm run telegram:webhook -- set      # вебхук на <адрес стенда>/api/telegram/webhook
   npm run telegram:webhook -- info     # куда смотрит вебхук, последняя ошибка доставки
   npm run telegram:webhook -- delete   # снять вебхук
   ```

Без токена канал выключен: вебхук отвечает 404, остальное приложение работает как обычно. Без секрета вебхук закрыт (503). Запросы без верного заголовка `X-Telegram-Bot-Api-Secret-Token` отклоняются. Telegram получает ответ сразу, а агент отвечает клиенту из фона: так медленный ответ модели не вызывает повторов. Повтор того же обновления второй раз не обрабатывается.

## API

| Метод | Что делает |
|---|---|
| `POST /api/chat` `{text, conversationId?}` | ответ агента: `{conversationId, text, sources, drafts, escalated}`; лимит 12 сообщений в минуту на адрес и общий на процесс |
| `GET /api/chat/:id` | история диалога |
| `POST /api/telegram/webhook` | вебхук бота Telegram; нужен заголовок `X-Telegram-Bot-Api-Secret-Token` |
| `GET /api/manager/conversations?status=` | очередь обращений |
| `GET /api/manager/conversations/:id` | переписка, КП, счета, эскалации, запуски агента |
| `GET /api/manager/stats?days=7` | обращения, эскалации, ₽, медиана времени ответа, пробелы базы знаний |
| `GET /api/manager/proposals/:id/pdf` | PDF черновика КП |
| `POST /api/manager/proposals/:id/approve` · `reject` | решение менеджера по КП |
| `POST /api/manager/conversations/:id/reply` `{text, remember?}` | ответ менеджера клиенту; `remember: true` — агент запомнит ответ |
| `DELETE /api/manager/learned/:slug` | забыть выученный ответ менеджера |
| `GET /api/manager/kb` · `GET /api/manager/kb/:id` | статьи базы знаний; одна статья — текстом в markdown |
| `POST /api/manager/kb` · `PUT /api/manager/kb/:id` `{title, content}` | новая статья или правка: текст режется на фрагменты, эмбеддинги пересчитываются |
| `DELETE /api/manager/kb/:id` | удалить статью |
| `POST /api/manager/escalations/:id/resolve` | закрыть эскалацию |

Панель менеджера открывается только с токеном (`Authorization: Bearer <NUXT_MANAGER_TOKEN>`). Если токен не задан, панель закрыта.

## Проверка качества

```
npm test                                                   # модульные тесты
npm run eval -- ollama qwen3.5:9b --file eval/questions-softline.json
```

`eval/questions-softline.json` — 43 вопроса по реальному каталогу и базе знаний, плюс сквозной сценарий для видео (`demo`). Вопросы разбиты на шесть групп: цена, подбор, российский аналог, условия, КП, эскалация. По каждому ответу проверяется:
- тот ли вид ответа (ответ, КП или передача менеджеру);
- названа ли нужная позиция;
- совпадает ли цена с каталогом;
- есть ли обязательные слова и нет ли запрещённых.

Результаты пишутся в `eval/results-*.json`.

## Сценарий видео

«Не знаю, что нужно, хотим защитить почту и файлы на 50 сотрудников» → три уточнения → два варианта из каталога → «а российский аналог?» → черновик КП → менеджер смотрит PDF и подтверждает. Затем цикл обучения: вопрос, на который агент не знает ответа, → менеджер отвечает с отметкой «Запомнить» → новый клиент задаёт тот же вопрос, и агент отвечает сам.

## Ограничения стенда

Каналы — чат на сайте и Telegram. Приёма входящей почты в этой версии нет: письмом уходит только КП после подтверждения менеджером. Продавец на документах вымышленный («ООО Демо Софт»). Логотипов и реквизитов заказчика в репозитории нет. Срок поставки в фиде не указан, поэтому агент его не называет и предлагает уточнить у менеджера. Признак «в реестре» берётся из фида как есть.
